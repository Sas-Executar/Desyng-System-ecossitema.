# [Engenharia] · AKW-M06-P01



  

Resumo Executivo

Essas 10 skills formam praticamente um ciclo completo de engenharia de software. Algumas atuam antes de escrever código, como architecture e system-design; outras durante a implementação, como code-review e debug; outras controlam qualidade e entrega, como testing-strategy e deploy-checklist; e algumas mantêm o sistema operável ao longo do tempo, como incident-response, documentation e tech-debt.

Conclusão

|   |   |   |   |
|---|---|---|---|
|ID|Skill|Em português|Para que serve|
|S01|architecture|Arquitetura de software|Definir a estrutura técnica geral do sistema|
|S02|code-review|Revisão de código|Verificar qualidade, erros e aderência aos padrões|
|S03|debug|Depuração|Investigar e corrigir defeitos|
|S04|deploy-checklist|Checklist de implantação|Validar se uma versão pode ser publicada com segurança|
|S05|documentation|Documentação técnica|Registrar como o sistema funciona e como deve ser usado|
|S06|incident-response|Resposta a incidentes|Diagnosticar e coordenar falhas em produção|
|S07|standup|Daily / acompanhamento diário|Consolidar progresso, bloqueios e próximas ações|
|S08|system-design|Projeto de sistemas|Desenhar tecnicamente uma funcionalidade ou sistema|
|S09|tech-debt|Dívida técnica|Identificar e priorizar problemas técnicos acumulados|
|S10|testing-strategy|Estratégia de testes|Definir como a qualidade será verificada|

Desenvolvimento

- S01 · Architecture — Arquitetura

- Define a estrutura macro do software.
- Decide como frontend, backend, banco, autenticação, APIs, filas e serviços se relacionam.
- Ajuda a escolher padrões como monólito, modular monolith, microsserviços, event-driven etc.
- Produz normalmente: arquitetura de referência, componentes, dependências, decisões técnicas e ADRs.
- Exemplo: decidir como Next.js, Supabase, Redis e um agente de IA se conectam no aplicativo.

- S02 · Code Review — Revisão de código

- Analisa código já escrito.
- Procura bugs, duplicações, problemas de segurança, legibilidade e performance.
- Verifica se o código segue padrões do projeto.
- Pode avaliar PRs antes de merge.
- Produz normalmente: comentários, problemas encontrados e alterações recomendadas.
- Exemplo: revisar uma Server Action antes de integrar na branch principal.

- S03 · Debug — Depuração

- É usada quando algo não funciona como esperado.
- Investiga erro, stack trace, logs, estado, banco de dados e fluxo de execução.
- Busca a causa raiz em vez de simplesmente alterar código aleatoriamente.
- Produz normalmente: hipótese → evidência → causa raiz → correção.
- Exemplo: descobrir por que uma tarefa criada no frontend não aparece no Supabase.

- S04 · Deploy Checklist — Checklist de implantação

- Atua imediatamente antes de colocar uma mudança em produção.
- Verifica itens críticos: testes, migrations, variáveis de ambiente, segurança, rollback e observabilidade.
- Evita publicar uma versão tecnicamente incompleta.
- Produz normalmente um checklist de PASS / FAIL / BLOCKED.
- Exemplo:

- testes passaram;
- migration validada;
- env vars configuradas;
- rollback disponível;
- monitoramento ativo.

- S05 · Documentation — Documentação

- Transforma conhecimento técnico em documentação reutilizável.
- Pode documentar APIs, componentes, decisões, setup, arquitetura, processos e troubleshooting.
- É importante para humanos e também para agentes de IA.
- Produz normalmente: README, SPEC, API docs, runbooks, ADRs e guias.
- Exemplo: documentar como um módulo de autenticação deve ser configurado e mantido.

- S06 · Incident Response — Resposta a incidentes

- É usada quando o sistema já está em produção e ocorre uma falha relevante.
- Organiza investigação, contenção, recuperação e análise posterior.
- Diferente de debug: debug pode resolver um bug qualquer; incident-response organiza uma ocorrência operacional real.
- Produz normalmente:

- impacto;
- severidade;
- timeline;
- mitigação;
- causa;
- ações preventivas.

- Exemplo: sistema ficou indisponível após um deploy.

- S07 · Standup — Acompanhamento diário

- Resume o estado do trabalho de engenharia.
- Estrutura tipicamente:

- o que foi feito;
- o que está em andamento;
- bloqueios;
- próximo passo.

- Pode consultar issues, PRs, commits e tarefas.
- Serve como camada de coordenação operacional.
- Exemplo:

- concluído: autenticação;
- atual: integração Supabase;
- bloqueio: schema pendente;
- próximo: testes E2E.

- S08 · System Design — Projeto de sistemas

- Desenha como um sistema ou funcionalidade específica deve funcionar.
- É mais concreto que architecture.
- Pode especificar:

- fluxo;
- APIs;
- banco;
- componentes;
- cache;
- concorrência;
- escalabilidade;
- tratamento de falhas.

- Exemplo: desenhar todo o sistema de notificações do aplicativo.

- A diferença principal é:  
    Architecture = organização estrutural do sistema inteiro.  
    System Design = desenho técnico detalhado de um sistema ou capability.
- S09 · Tech Debt — Dívida técnica

- Identifica decisões antigas ou atalhos que estão prejudicando o sistema.
- Pode encontrar:

- código duplicado;
- dependências antigas;
- testes ausentes;
- arquitetura inconsistente;
- hacks temporários;
- módulos difíceis de manter.

- Ajuda a priorizar o que deve ser corrigido.
- Produz normalmente: inventário de dívida + impacto + prioridade + plano de redução.
- Exemplo: identificar que três partes do sistema implementam autenticação de formas diferentes.

- S10 · Testing Strategy — Estratégia de testes

- Decide o que testar, como testar e em qual nível.
- Pode definir:

- unit tests;
- integration tests;
- E2E;
- contract tests;
- performance;
- security;
- regression.

- Não significa simplesmente “executar testes”.
- Define a arquitetura de qualidade do projeto.
- Exemplo:

- regras de negócio → unit;
- Supabase → integration;
- jornada usuário → E2E;
- API → contract test.

Próximos Passos

Para um agente de desenvolvimento do seu aplicativo, eu organizaria essas skills em quatro blocos operacionais: Planejar (architecture, system-design), Construir e corrigir (code-review, debug), Validar e publicar (testing-strategy, deploy-checklist) e Operar e evoluir (incident-response, documentation, standup, tech-debt). Essa divisão é especialmente útil para transformar as skills da Anthropic em workflows agenticos do seu próprio repositório.





Próximos Passos. A partir deste blueprint, eu estruturaria a proposta do produto em três camadas: Core Proposition: “Execution OS para trabalhador solo”; Core Engine: Plan → Eligibility → Dispatch → Execute → Evidence → Learn; Core Experience: “Quanto tempo/capacidade você tem agora?” → “Faça isto agora” → executar → concluir com DoD → próxima ação. O que deve permanecer fora do núcleo inicial são CRM, Service Desk, colaboração empresarial pesada e customização ilimitada; eles podem surgir depois como módulos ou workflows sobre a infraestrutura central, sem diluir a proposta principal.
